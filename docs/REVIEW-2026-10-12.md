# Full-stack review — job posting & production breakage (2026-10-12)

Scope: backend, frontend, database layer, branding. Every finding below was
**reproduced against a running system first** (real API on SQLite *and* real
Postgres 16, real Chromium driving the UI), then fixed, then covered by a
regression test that was confirmed to fail on the old code.

## Why production broke while every test was green

The dev database and the whole test suite run on **SQLite**; production runs on
**Postgres** (see `render.yaml`). The code is written in SQLite's dialect and
`server/db.js` translates it at runtime. Nothing ever ran the app against
Postgres, so every place where the two engines disagree shipped to production
unnoticed. Four of the findings below are exactly that.

## Findings and fixes

### Job posting (`POST /api/jobs`)

| # | Symptom | Cause | Fix |
|---|---------|-------|-----|
| 1 | Posting fails at random, then **always** once a month fills up | `job_code` had only 9,000 values/month behind a `UNIQUE` constraint, with no retry (≈1% of posts fail at 100 jobs/month, ≈11% at 1,000) | Retry on collision with a fresh code; later attempts widen to 6 digits (`lib/http.js`, `validators/job.schema.js`) |
| 2 | Error "pickupLat: Too small: expected number to be >=22" on a field the user never touched | zod `coerce.number()` turned a blank/`null` into `0`, then rejected it | Blank/`null` = "not provided"; out-of-range map pins are dropped rather than blocking the post; every message now names the field in plain language (`middleware/validate.js`) |
| 3 | A "failed" post (HTTP 400) still created a live job → ghost duplicates in Open Loads | Cargo-value / insurance validation ran *after* the INSERT; extra rows were separate follow-up statements | All validation runs before the first write; the job, line items and terms record are one transaction |
| 4 | Garbage `readyAt` ("tomorrow"), or a deadline before the ready time, accepted | Columns are `TEXT`; nothing parsed them | Validated, ordered, and stored as normalised ISO-8601 |
| 5 | Double-click on "Post job" can create two jobs (Postgres) | Idempotency row was written only *after* success, so concurrent same-key requests both ran | In-flight guard in `lib/idempotency.js` |
| 6 | Attaching a 2–5 MB packing list fails with `413 request entity too large` *after* the job was posted | UI allows 5 MB; server JSON cap was 2 MB (base64 adds ~33%) | 8 MB cap on the six upload routes only; friendlier client messages |
| 7 | Stale time slot survives switching the date to *today* | `TimeSlotPicker` kept the old hour | Cleared when it would be in the past |
| 8 | Finance/viewer seats and unapproved accounts get a dead end | Button disabled with no reason / raw `Seat role VIEWER not in [OPS]` | Reason shown at the button; readable server message |

### Postgres-only production bugs (invisible to the SQLite suite)

| # | Symptom | Cause | Fix |
|---|---------|-------|-----|
| 9 | **500 `function max(integer, real) does not exist`** on cancel-with-penalty, dispute resolution, credit repayment | SQLite's scalar `MAX(a,b)` doesn't exist in Postgres | `lib/sqlTranslate.js` rewrites to `GREATEST`/`LEAST` (7 call sites fixed at once) |
| 10 | Search boxes return nothing unless capitalisation matches (`lb-1008` → 0, `LB-1008` → 1) | SQLite `LIKE` is case-insensitive, Postgres `LIKE` is not | `LIKE` → `ILIKE` in the translator |
| 11 | API returned `{"total":"28"}` (string) instead of `28` | node-pg returns `BIGINT`/`NUMERIC` as strings | Type parsers registered once (`lib/pgTypes.js`) |

### Frontend

| # | Symptom | Fix |
|---|---------|-----|
| 12 | `/edi/consignments` crashed (`Cannot read properties of undefined (reading 'toLowerCase')`) for every shipper with a consignment; "Linked Job" always "—" | Page read a field (`consignment_id`) the API never returns; now uses `id`, null-safe, API returns `job_code` |
| 13 | Dark theme: current page's sidebar label is dark-on-dark | Sidebar is dark in both themes; label colour pinned to white |
| 14 | Dark-mode users get a light flash on every load (Express-served build) | CSP blocked the inline theme script; allowed by SHA-256 hash only |
| 15 | Generated documents (invoice, settlement, POD…) never showed the logo | Linked by relative URL but opened from a `blob:` URL, so it couldn't resolve; now embedded as a data URI |

### Branding

The supplied pack (white wordmark, wordmark on navy, container icon) is now used
everywhere: app header/sidebar/footer/drawer, marketing nav + hero, login and
auth panels, favicons + `apple-touch-icon` + PWA icons, social card
(`og-image.png`), JSON-LD, transactional e-mails (newly branded), generated
documents, README. The old SVG wordmark drew its letters with live `<text>`,
which cannot use web fonts when loaded through `<img>`, so it rendered
differently per OS (and its "BY" was invisible on navy); the supplied PNG art
is used instead. See `docs/brand/BRAND_GUIDELINES.md`; regenerate assets with
`python3 scripts/generate-brand-assets.py`. The pack has no dark-on-light
wordmark, so one was derived by recolouring white → brand navy (`#0F2B3D`).

## Verification

* Server suite on SQLite: all green (`npm test`).
* Server suite on Postgres, each file in its own schema: see `npm run test:pg`.
* Playwright e2e (18 specs + new EDI spec) green on **both** engines.
* Wizard driven in Chromium on Postgres: LOCAL, EXPORT, multi-container +
  3 MB packing list, CUSTOM equipment, scheduled post, unapproved account.
* Every SPA route as every role, and every `GET` route as every role, swept for
  runtime errors and 5xx: clean after the fixes above.

## Not changed — worth a decision

* **Google Analytics is blocked by the CSP** on the Express-served build (the
  inline loader and `googletagmanager.com` aren't allowed). Allowing it means
  whitelisting third-party hosts on pages that show financial data, so it was
  left for the owner to decide.
* **`byIp()` trusts the spoofable `cf-connecting-ip` header** (`lib/rateLimit.js`).
  Unless the API is genuinely behind Cloudflare, per-IP auth throttling can be
  bypassed by rotating that header. Fixing it safely needs to know the real
  proxy topology (a blanket change would make every user share one limit).
* `POST /api/auth/login` answers bad credentials with **403**, not 401.
* The 6 upload routes now accept 8 MB bodies *before* authentication.
* `server/lib/database.js` is unused dead code.
